# @textadventures/graph-map

A map of a directed graph, as a Svelte 5 component, with a live force-directed layout. Built for the Squiffy editor's story map (#380), and meant for Quest Viva's map of rooms too.

It has **no Squiffy imports**, so it can become a standalone package later, as `project-fs` can (#215). For now it's a private workspace, versioned with the rest of the repo.

```bash
npm run build   # the TypeScript core, into dist/
npm test
npm run check   # svelte-check, including the component
```

## What's in it

- **`GraphMap.svelte`** (`@textadventures/graph-map/GraphMap.svelte`, shipped as source for the app's Svelte build): draws the graph, with its nodes as SVG and its edges on a canvas underneath. Pan (drag the background, or scroll), zoom (pinch, Ctrl/Cmd+scroll, + and -), fit (0), drag a node (which pins it where it's dropped), drag-to-link from the selected node's handle, double-click to create, and keyboard access: the arrow keys move between nodes, Enter opens one, F2 renames it, and a live region reads out each node's `description`. Edges longer than `longEdge` are faint, unless hovered or an end is selected, so that links across the map don't hide those between neighbours. Its colours are CSS variables (`--gm-node-fill` and friends) that follow the page's `color-scheme`, and the host styles nodes and edges through their `class`, or draws nodes itself with the `node` snippet.
- **`MapModel`**: the live state apart from drawing, so it can be tested without a DOM. It keeps the map stable as the graph changes: nodes the host has pinned never move (unless dragged); when nodes are added, the ones already there are held still, apart from the new nodes' neighbours, until it settles; dragging a node (or several, selected with a Shift+drag lasso or Shift+click) moves its satellites and any node linked only to it, which would otherwise be stranded, while everything else is held still, so nothing drifts into the space it leaves. Once the map settles, wherever each node got to becomes where the layout holds it. `rename()` keeps a node's place when its id changes.
- **`Simulation`** and the **forces** (`manyBody`, `springs`, `towards`, `collide`): in the style of d3-force. Repulsion uses a Barnes–Hut quadtree, so it's O(n log n), and collision a grid. Everything is seeded, so the same graph gives the same map on every machine.
- **Layouts** are pluggable (`Layout`: where new nodes start, and the forces). **`layeredLayout()`** is a directed force layout: each node is pulled towards a row given by its rank (in Squiffy, the longest way to it from the start, leaving out links back round loops), first placed in rows ordered by the barycentre of their parents to cut down crossings; when there are so many rows that the map would be much taller than the screen (its `aspect`), they fold into columns side by side, like a newspaper's, cut where fewest edges cross between columns, with the edges between columns hardly pulling, and a row added later goes in the column of the row above it, so the columns stay put until the map is laid out afresh; "satellite" nodes (Squiffy's passages) are held under their parent, three to a line, and each row is as tall as what hangs under it; boxes in rows push each other apart sideways rather than out of their row; and groups (Squiffy's unreachable sections) start side by side. A Quest Viva room map would want a layout that keeps exits in their compass directions instead.
- **Geometry and viewport** helpers: edges clipped to boxes, curved apart when there's more than one between two nodes, arrowheads, fitting and revealing.

## Performance

Nodes are SVG, and their positions are written to the DOM directly on each frame (as CSS transforms), not through Svelte's template, which would revisit every node each frame. Edges are drawn on a canvas under the nodes, batched by style, as an SVG element for each was far too slow to redraw: a story with 4,000 links managed 3–4 frames a second while it laid itself out, and one with 50,000 under 2. They're still styled with CSS: for each combination of an edge's `class` and state (`gm-edge-selected`, `gm-edge-hover`, `data-long`), the component reads the computed style of a hidden `<g class="gm-edge …">` holding a `.gm-edge-line` and a `.gm-edge-arrow`, so the host's selectors work as they would on SVG edges. These are looked up again when an attribute on `<html>` changes, or the system's colour scheme, in case the theme has. Hovering and clicking edges is worked out from their geometry.

A simulation tick takes about 0.5 ms at 300 nodes (bigger than 99% of the stories on textadventures.co.uk), 1.3 ms at 700, 3.6 ms at 1,500 and 8 ms at 3,000, so it runs on the main thread. The first layout runs as many ticks as fit in 12 ms a frame. Once drawing a frame takes more than 8 ms, a frame either moves the nodes or draws them, and drawing gets at most half the time, so no piece of work is long enough to make the page stutter. Measured in Chrome on real stories: one with 1,900 sections and passages and 4,000 links runs at about 20 frames a second as it lays itself out, and one with 4,100 and 49,000 links at about 30, settling in 12 seconds. The editor asks before drawing a story of more than 6,000 sections and passages: only two generated test stories are that big. One of 14,000 runs at about 19 frames a second but keeps the main thread busy for 40 seconds. If that's ever needed, the simulation could move to a worker.
