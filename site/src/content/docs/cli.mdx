## Installing

As an alternative to the [web editor](https://app.squiffystory.com), Squiffy is also available as a command-line Node package. This runs on Windows, Mac and Linux.

To install the Squiffy compiler, first [install Node.js](https://nodejs.org/).

You can then run the CLI directly using `npx`, in your story's folder:

```bash
npx @textadventures/squiffy-cli
```

`npx` downloads Squiffy the first time, and runs it. Alternatively, install it globally:

```bash
npm install @textadventures/squiffy-cli -g
```

Then you can run it as `squiffy-packager`.

## Usage

A Squiffy story is a folder with a [`squiffy.json` project file](/multiple-files/) in it, which names the story's main `.squiffy` file. Every story made in the [editor](https://app.squiffystory.com) has one, and so does every story converted by the CLI. To start one by hand, create the folder, write your story in a `.squiffy` file, and add a `squiffy.json` next to it as shown in [Stories in several files](/multiple-files/).

Squiffy files are text files with a `.squiffy` file extension. You can write them in any text editor - Notepad, [VS Code](https://code.visualstudio.com/), [Sublime Text](https://www.sublimetext.com/), TextEdit etc.

To turn your story into a working browser-based game, go to its folder in a command prompt and type:

```bash
npx @textadventures/squiffy-cli
```

Giving it the folder, or the main file named in `squiffy.json`, does the same. Every `.squiffy`, `.css` and `.js` file in the folder is part of the story.

Squiffy writes the game to a `build` folder next to `squiffy.json`, so it's kept apart from your story's own files:
- `index.html` - the main HTML page
- `style.css` - the stylesheet
- `story.js` - your compiled story
- `squiffy.runtime.global.js` - the Squiffy runtime

It copies the story's stylesheets and scripts there too, with its images and other files, so the `build` folder is the whole published story. `--zip` and `--scriptonly` write there as well, and `--serve` serves it. Files left in the `build` folder from an earlier build aren't removed, so delete the folder first if you want a clean copy.

Launch `build/index.html` to play the game.

The `build` folder can now be uploaded anywhere, and it will run entirely locally in the player's web browser (your `.squiffy` files don't need to be included).

The browser's local storage will be used to save the state of the game. This means the player can close their browser, and the next time they go back to that page, the game will resume from where they left off.

**Note: Even if you recompile a game, the previous state will still be loaded.** This means that after making a change to your game, you'll need to click the Restart button at the top of the screen to see your changes.

### Stories without a squiffy.json

Give Squiffy a `.squiffy` file that isn't the main file in `squiffy.json`, or one in a folder with no `squiffy.json`, and it builds just that file and whatever it `@import`s:

```bash
npx @textadventures/squiffy-cli mygame.squiffy
```

The four files are written next to it, rather than to a `build` folder. Squiffy says when it does this. So a folder can still hold several separate stories.

A story without a `squiffy.json` uses Squiffy 6's rules for [setting attributes](/attributes/#setting-attributes), so Squiffy 6 stories still build unchanged. To bring one up to date, see [Converting from Squiffy 6](#converting-from-squiffy-6).

### Errors and warnings

If your script has a problem, Squiffy prints it with the file and line number:

```text
WARNING: mygame.squiffy line 12: In section 'kitchen' there is a link to a section called [[cellar]], which doesn't exist
ERROR: mygame.squiffy line 30: Can't add passage "look" as no section has been created.
```

A warning, such as a link to a section or passage that doesn't exist, points at the line the problem is on, and the game is still created. A hint, such as an `@import` that isn't needed, is a suggestion. An error stops the game being created, so fix it and run Squiffy again.

## Checking a story

Use `--check` to look for problems without building anything:

```bash
npx @textadventures/squiffy-cli --check
```

As well as the errors and warnings a build shows, this finds the problems the [editor](/editor/) shows: sections that can't be reached from the start of the story, dead ends, which are sections with no way out that aren't marked with `@end`, and [sound on the story's first screen](/images-and-files/#music-and-sound), which browsers won't play until the player clicks something. Each problem is shown with its file, line and column:

```text
story.squiffy:12:5: warning: The section "cellar" has no way out, as it has no links to another section. If it's one of the story's endings, add @end to say so. [squiffy/dead-end]

24 sections and 6 passages, starting at "intro", with 2 endings: "escaped", "eaten".
0 errors, 1 warning.
```

The errors include mistakes in `{{...}}` text that would stop a section or passage being shown, such as an expression that needs an `=` (`{{round + 1}}` rather than `{{= round + 1}}`), or an `{{#unless}}` closed by `{{/if}}`. These stop the story building, as the build and the editor report them too:

```text
story.squiffy:7:19: error: In section 'start', {{round + 1}} isn't valid Handlebars. To show the result of an expression, start it with "=": {{= round + 1}} [squiffy/template-syntax]
```

The build, the editor and `--check` also warn about a `{{name}}` that isn't a helper when nothing in the story sets an attribute called `name`, as it shows nothing. That's usually a typo, such as `{{glod}}` for `{{gold}}`, or a [helper of your own](/javascript/#creating-custom-helpers) that hasn't been added. An attribute counts as set if the story sets it anywhere: with `@set`, `@inc`, a link, `{{set}}`, a [text box](/player-input/), an [embed](/basic-concepts/#parameters), or `squiffy.set("name", ...)` in its JavaScript.

It finishes with an exit code of 1 if there are any errors.

### Turning off a warning

A warning can be wrong about your story, or be something you've chosen to do. If the page your story is [embedded](/embedding/) in always has a click first, music on the first screen will play, and an attribute your JavaScript sets in a way Squiffy can't see, such as `squiffy.set(name, ...)` with a name that's worked out as it runs, is set after all. To turn a warning off, put a comment in the section it's about, naming the warning's code (what comes after `squiffy/` in the brackets):

```squiffy
[[start]]:
@music theme.mp3
{{!-- squiffy-ignore sound-on-first-screen --}}
Welcome aboard.
```

That turns the warning off for that section and its passages. A comment in the [master section](/basic-concepts/#master-sections-and-passages) turns it off for the whole story. After the code, you can name which attributes an `unknown-name` warning is turned off for, so others are still reported:

```squiffy
[[]]:
{{!-- squiffy-ignore unknown-name board score --}}
```

Players don't see the comment. It's part of the section's text, so if the section has JavaScript, put it after that. In the editor, the quick fix for these warnings adds it for you. Errors can't be turned off.

## Playing a story from the command line

Use `--play` to play a story as text, without a browser. Squiffy shows the text the player would see, with the links they can click in `[brackets]`, and lists the links, with where each one goes:

```bash
npx @textadventures/squiffy-cli --play
```

```text
(section "intro")

You're standing outside a coffee shop. [Go inside] or [look around].

Choices (in section "intro"):
  1. Go inside -> section "shop"
  2. look around -> passage "look around"
```

A section without a name of its own, one that starts with a `+++` or `---` line, is called by that line and the named section before it, such as `the "+++Continue..." after "cellar"`, or `the second "+++Continue..." after "cellar"` if there's more than one.

To click a link, add `--choose` with the link's text or its number:

```bash
npx @textadventures/squiffy-cli --play --choose "look around"
```

You can add `--choose` as many times as you like, and the links are clicked in order. To click a lot of them, put them in a file, one on each line, and give it with `--choices links.txt`. Blank lines, and lines starting with `# `, are left out. The links in the file are clicked first, then any `--choose`.

### Playing a few links at a time

Add `--save` with a file name to carry on from where you left off. Squiffy loads the game saved in the file, if there is one, clicks the links you give it, and saves the game there again. So you can play a story a link or two at a time, deciding what to click next from what you see:

```bash
npx @textadventures/squiffy-cli --play --save game.json
npx @textadventures/squiffy-cli --play --save game.json --choose "Go inside"
npx @textadventures/squiffy-cli --play --save game.json --choose 2
```

The saved game keeps the text that's on the screen, so if you change the story, that text stays as it was, though what comes next is from your changes. Delete the file, or use `--start`, to start again.

### Other options

- `--input attribute=value` puts text in a [text box](/player-input/), when there is one for that attribute on the screen. Add it once for each text box.
- `--start section` starts at another section.
- `--attributes` shows the story's [attributes](/attributes/) at the end.
- `--seed 42` makes anything random in the story, such as [`{{random}}`](/dynamic-text/#random), happen the same way every time.

Any errors in the story, such as a mistake in its JavaScript, are shown where they happen, and Squiffy finishes with an exit code of 1. Time passes at once: animations finish straight away, and a [`{{goto}}`](/basic-concepts/#go-to-another-section) with `after=` happens without waiting. [`{{#every}}`](/dynamic-text/#repeating-text) text is shown again and again too, until it stops, or until it has been shown 20 times in a row with nothing else to wait for, when play carries on with the text as it is then. Text from `{{#animate "continue"}}` is shown as a link to click. Script files that a story adds to its page aren't run.

### Playing at random

Use `--random` to play the story many times, clicking links at random, to find problems you might not come across yourself:

```bash
npx @textadventures/squiffy-cli --random
```

It plays 20 times, or as many as you say (`--random 100`), clicking up to 200 links each time, or as many as you say with `--steps`. Text boxes are filled in with something that fits. Then it lists the sections and passages it never got to, the endings it reached, and any problems: errors, and dead ends it got stuck at. For each problem, it gives the options to play the story to it again:

```text
Error in section "shop" (4 times): gold is not defined
  To get there: --play --seed 1234 --choose 'Go inside' --choose 'Buy a coffee'
```

When it takes more than five links to get to a problem, they're written to a file for `--choices`, in a `random` folder where the story is built (the `build` folder, or next to the file for a story without a `squiffy.json`):

```text
Dead end in section "Ending" (20 times): There are no links to click, and the section isn't marked @end.
  To get there: --play --seed 7 --choices build/random/problem-1.txt
```

Use the same `--seed` to play the same way again.

## Testing a story

A playthrough test is a way through your story that you've recorded, to play again after you've changed the story, to check it still goes the same way. Tests run from the command line, so they can run in a CI workflow too, such as GitHub Actions, every time you push a change.

### Recording a test

Add `--record` to `--play`, with the file to record the test to:

```bash
npx @textadventures/squiffy-cli --play --input name=Sam --choose "Go inside" --choose "Buy a coffee" --record tests/coffee.squiffy-test
```

Squiffy plays the story as usual, and writes down the links clicked, and after each one, the sections and passages it went to, and the [attributes](/attributes/) it changed. It also writes down the seed, any `--input` and any `--start`, so the test plays the story the same way every time, including anything random. Give a `--seed` to choose the seed, or Squiffy picks one. A test isn't recorded if play stops early, such as at a link that isn't there, or the story has an error.

The test is a text file, which you can read, and change by hand:

```text
# A playthrough of the story, recorded with --play --record.
# Run it with --test, or record it again with --test --update.
seed 150030
input name=Sam

went "intro"

> Go inside
went "shop"
set gold = 10

> Buy a coffee
went "shop" "Buy a coffee"
set gold = 7
set coffee = true
```

A `> ` line is a link to click. `went` is a section the story went to, or a section and a passage. `set` is an attribute that changed, with its new value, and `unset` is one that was removed. The lines before the first `> ` are for the start of the story. The `turns`, `previous` and `previous_section` attributes, which change with every link clicked, are left out.

#### Ignoring attributes

Some attributes are only the story's own bookkeeping, such as one that remembers whether some text has been shown. If you change how the story keeps track of that, the test fails, even though the story plays the same. To leave attributes out of a test, add `--ignore` when you record it, with the attributes' names. A `*` matches any characters, so `seen_*` ignores `seen_hall`, `seen_kitchen` and so on:

```bash
npx @textadventures/squiffy-cli --play --choose "Go inside" --ignore told --ignore "seen_*" --record tests/coffee.squiffy-test
```

This adds an `ignore` line to the test, before the first `went`, and the test doesn't record or compare those attributes:

```text
seed 150030
ignore told seen_*
```

You can add an `ignore` line to a test you've already recorded too. `ignore *` ignores every attribute, so the test only checks the links, sections and passages. `--test --update` keeps a test's `ignore` lines when it records it again.

### Running the tests

Use `--test` to run every `.squiffy-test` file in the story's folder, and the folders in it, apart from the `build` folder:

```bash
npx @textadventures/squiffy-cli --test
```

Add a file or folder to run just those tests: `--test tests/coffee.squiffy-test`. For each test that fails, Squiffy says where the story went differently, which is often enough to see what changed:

```text
PASS tests/coffee.squiffy-test
FAIL tests/tea.squiffy-test
  At step 3 (> Buy a tea):
    gold was set to 6, but expected set to 7.

2 tests: 1 passed, 1 failed.
```

A test fails if a link it clicks isn't there any more, the story goes to a different section or passage, an attribute it doesn't ignore is set to something different, or there's an error. Squiffy finishes with an exit code of 1 if any test fails.

If you changed the story on purpose, add `--update` to record the tests that fail again, as the story plays now. A test that stops at a link that isn't there any more, or has an error, can't be recorded again: change the link in the test file, or record it again with `--play --record`.

### For AI agents

These options let an AI agent, such as Claude Code, check a story it's helping you write, and play through it, without a browser. Add `--json` to `--check`, `--play`, `--random` or `--test` to print the result as JSON, for the agent, or any other program, to read. See [Writing with an AI agent](/writing-with-ai/), which also covers the Squiffy plugin for Claude Code.

To learn how to write a Squiffy story, an agent can read these docs as Markdown: [llms.txt](/llms.txt) introduces Squiffy and these options, [llms-full.txt](/llms-full.txt) has every page in one file, and [llms-small.txt](/llms-small.txt) leaves out the editor's pages and the long examples.

## Output Formats

Squiffy supports different output formats depending on how you want to distribute your game.

### Standard (multiple files)

The default output creates four separate files as described above. This is ideal for:
- Hosting on a web server
- Situations where you want to customize the HTML or CSS
- Development and debugging (easier to inspect individual files)

### Single HTML file (inline)

Use `--inline` to create a single self-contained HTML file with all CSS, JavaScript, and story content embedded:

```bash
npx @textadventures/squiffy-cli --inline
```

This creates just one file: `index.html`. This is ideal for:
- Easy sharing (just send one file)
- Uploading to platforms that only accept a single HTML file
- Offline distribution
- Embedding in other documents

### Zip file

Use `--zip` to also create a zip archive of the output files, called `output.zip`:

```bash
npx @textadventures/squiffy-cli --zip
```

You can combine this with `--inline` to create a zip containing just the single HTML file:

```bash
npx @textadventures/squiffy-cli --inline --zip
```

### Images and other files

Images, sounds and other files that your story [refers to](/images-and-files/) are included automatically, as long as they're in the story's folder or a folder below it:

- With the standard output, they're copied into the `build` folder. For a story without a `squiffy.json`, they're already in the right place, next to `index.html`.
- With `--zip`, they're added to `output.zip` at the same paths.
- With `--inline`, they're embedded in `index.html` as data URIs, so the single file still works on its own. This makes the file about a third bigger than the files themselves, so large sound or video files are better shared with `--zip`.

Squiffy looks for file names in your story text, JavaScript and stylesheets with these extensions: `apng`, `avif`, `bmp`, `gif`, `ico`, `jpeg`, `jpg`, `png`, `svg`, `webp`, `aac`, `flac`, `m4a`, `mp3`, `oga`, `ogg`, `opus`, `wav`, `weba`, `m4v`, `mp4`, `ogv`, `webm`, `vtt`, `otf`, `ttf`, `woff`, `woff2` and `pdf`. File names with spaces aren't found, so either avoid spaces or write them as `%20` (e.g. `my%20cat.png`).

## Options

### HTTP Server

Use `--serve` (or `-s`) to start a local HTTP server after compiling. Open the address it prints (e.g. `http://localhost:8282/`) in your browser to test your game:

```bash
npx @textadventures/squiffy-cli --serve
```

Optionally specify a port using `--port` (or `-p`):

```bash
npx @textadventures/squiffy-cli --serve --port 3000
```

The default port is 8282.

### Script only

Use `--scriptonly` to generate *only* the `story.js` file, without overwriting the other files. This is useful when you've customized `index.html` or `style.css` and only want to update the story:

```bash
npx @textadventures/squiffy-cli --scriptonly
```

You can optionally specify a custom filename:

```bash
npx @textadventures/squiffy-cli --scriptonly myscript.js
```
### Converting from Twine

Use `--convert-twine` to convert a [Twine](https://twinery.org/) story, written in Harlowe or SugarCube, to Squiffy. Give it Twine's published or archive HTML file, or a Twee file:

```bash
npx @textadventures/squiffy-cli mygame.html --convert-twine
```

This creates a folder next to the file, with the same name (`mygame` here), with the Squiffy story in it, and `twine-import.txt`, which lists anything that couldn't be converted exactly. To put it somewhere else, add `--out` and a folder that's empty or doesn't exist yet. See [Converting a Twine story](/converting-from-twine/) for what's converted, and how.

### Converting from Quest

Use `--convert-quest` to convert a gamebook made in [Quest Viva](https://questviva.com), or Quest 5 as it was known before, to Squiffy. Give it the `.quest` file, or the `.aslx` file Quest saves:

```bash
npx @textadventures/squiffy-cli mygame.quest --convert-quest
```

This creates a folder next to the file, with the same name (`mygame` here), with the Squiffy story in it, the images and sounds the gamebook uses, and `quest-import.txt`, which lists anything that couldn't be converted exactly. To put it somewhere else, add `--out` and a folder that's empty or doesn't exist yet. See [Converting a Quest gamebook](/converting-from-quest/) for what's converted, and how.

### Converting from Squiffy 6

In a story with a `squiffy.json`, text in `@set` and link assignments goes in quotes, and attributes are written without an `@` (see [Coming from Squiffy 6](/coming-from-squiffy-6/)). A Squiffy 6 story has no `squiffy.json`, so it keeps the old rules. When the CLI builds one whose assignments would need changing, it says so. Use `--convert-v6`, giving it the story's main file, to convert it and add a `squiffy.json`:

```bash
npx @textadventures/squiffy-cli mygame.squiffy --convert-v6
```

This converts the main file and every `.squiffy` file it `@import`s, keeping each original as a `.bak` file. The new `squiffy.json` leaves out any other `.squiffy`, `.css` and `.js` files in the folder, so the story is made of the same files as before. From then on, the story is built into a `build` folder, so you can delete the `index.html`, `style.css`, `story.js` and `squiffy.runtime.global.js` that earlier builds left next to it. Anything that can't be converted exactly is left as it is, and listed with its line number so you can update it by hand. If the story still has Squiffy 5 syntax, run `--convert-v5` first.

### Converting from Squiffy 5

Squiffy 6 replaced the Squiffy 5 text processor syntax, such as `{if x:...}` and `{x}`, with [Handlebars](/dynamic-text/). When the CLI sees Squiffy 5 syntax in a story, it warns about it. Use `--convert-v5` to convert it to the Squiffy 6 equivalent:

```bash
npx @textadventures/squiffy-cli mygame.squiffy --convert-v5
```

This updates `mygame.squiffy`, keeping the original as `mygame.squiffy.bak`. Anything that can't be converted reliably is left as it is, and listed with its line number so you can update it by hand. Files included with `@import` aren't converted, so run the CLI on each of them too.
